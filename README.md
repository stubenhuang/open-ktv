# Open KTV

简易版全民K歌（Web）：**点歌或上传伴奏 → 跟唱歌词 → 戴耳机带耳返演唱 → 服务端合成 192kbps MP3 → 试听 / 调混音与音效 / 下载**。

单机自用，无需登录。伴奏可以传音频，也可以传视频（MV 会带画面播放）；可以从自建曲库源搜索点歌。

---

## 功能

| 模块 | 说明 |
|---|---|
| 伴奏库 | 拖拽上传（可多选）、列表试听、编辑歌名/歌手、删除；单文件上限 1GB |
| 点歌台 | 从配置好的曲库源搜索 → 点歌（服务端自动下载入库）→ 去演唱；带歌词的源会连歌词一起入库；重复点歌自动去重 |
| 歌词跟唱 | 支持 LRC（`[mm:ss.xx]`/多时间戳/`[offset:]`）；演唱页逐行滚动高亮、点行跳转、整曲对轴微调（±30s） |
| 格式兼容 | 浏览器能直接播的原文件直接用；mkv / avi / flv / h265 / ape 等**自动转码**成 mp4(h264+aac) 或 mp3 代理 |
| 演唱页 | 麦克风设备下拉（**只列外置输入**，内置麦克风默认隐藏）、实时音量条、伴奏音量 / 耳返音量两个滑块、人声耳返一键静音、MV 画面播放 |
| 录音 | 只录麦克风**干声**（WAV，采样点精确），伴奏不进录音文件 |
| 自动对齐 | 先起录 0.15 秒静音再放伴奏，用音频图上的起播探测器在渲染时钟精确测量伴奏真正起播的时刻，混音时人声提前这段间隔（偏移可为负） |
| 混音 | 人声音量 / 伴奏音量 / 四档混响 / 人声对齐微调；「实时试听」改动立即生效，点「合成」出 MP3 |
| 音效 / 修音 | 六档预设（自然/温暖/明亮/磁性/空灵/有力）、三段均衡、压缩量、去齿音、降噪 |
| 响度 | 干声与伴奏分别自动响度归一化，末端限幅防削波 |
| 作品库 | 列表、播放、下载 MP3、改名、删除；合成后自动定位到对应作品 |

## 环境要求

- **Node.js ≥ 22.6**（用到内置 `node:sqlite` 和原生 TypeScript 类型擦除；开发时用的是 24.2）
- **ffmpeg / ffprobe 在 PATH 里**（`ffmpeg -version` 能跑就行）
- **桌面 Chrome / Edge**（音频部分用了 AudioWorklet、MediaElementSource，只保证 Chromium 系）
- **一副有线耳机** —— 耳返和「不串音」都靠它

## 快速开始

```bash
npm install
./openktv.sh start
```

然后打开 <http://127.0.0.1:8787>。它会在当前终端前台跑、日志实时打出来，按 `Ctrl+C` 就关掉。

### 服务管理脚本 `openktv.sh`

推荐用它来开关服务：默认**占住当前终端前台跑**（日志实时打出来，`Ctrl+C` 关闭），
加 `--daemon` 才是放到后台。两种方式都会自动记 pid、写日志、检查端口。

```bash
./openktv.sh start            # 启动（生产模式：单进程，会先自动构建前端）——前台跑，Ctrl+C 关
./openktv.sh start --dev      # 启动开发模式（Vite 热更新 + 后端 --watch，改代码自动生效）
./openktv.sh start --daemon   # 放后台跑（不占终端），启动完就返回，用 stop 关
./openktv.sh stop             # 关闭
./openktv.sh stop --force     # 关闭，并清掉占着端口的残留进程
./openktv.sh restart          # 重启（沿用上次的模式，同样是前台跑）
./openktv.sh status           # 查看状态（运行中退出码 0，没运行退出码 1）
./openktv.sh logs             # 跟踪日志（Ctrl+C 退出，不会关掉服务）
```

前台模式下 `Ctrl+C` 一次是优雅关闭（先给服务发信号，最多等 10 秒收尾），再按一次就是强制结束。
不管前台后台，pid 都写在同一个 `.run/openktv.pid` 里，所以另开一个终端跑 `status` / `stop` 一样管用 ——
在别的终端 `stop` 掉之后，前台那个脚本会自己收尾退出。

| 模式 | 进程数 | 访问地址 | 说明 |
|---|---|---|---|
| `start`（默认，生产） | 1 | <http://127.0.0.1:8787> | 单进程同时托管前端和 API。每次启动都会重新构建前端（约 0.1 秒） |
| `start --dev` | 3 | <http://127.0.0.1:5173> | Vite HMR + 后端 `--watch`，改代码立刻生效 |

`--daemon` 只决定「占不占终端」，跟上面两种模式是正交的。

相关文件（都在 `.run/`，已 gitignore）：

- `.run/openktv.pid` —— 服务进程号
- `.run/openktv.mode` —— 上次用的模式，`restart` 会沿用它
- `.run/openktv.log` —— 服务和构建的完整日志

**换端口**：`PORT` 是后端，`WEB_PORT` 是开发模式下的前端，两个会一起生效
（`vite.config.ts` 的代理目标跟着 `PORT` 走）：

```bash
PORT=9000 WEB_PORT=5273 ./openktv.sh start --dev
```

### 不想用脚本的话

```bash
npm run dev              # 开发模式，前台跑，Ctrl+C 关
npm run build && npm start   # 生产模式，前台跑，Ctrl+C 关
```

前台跑的时候 `Ctrl+C` 一次就能把前后的进程都收干净（`dev.mjs` 做了信号转发）；
`./openktv.sh start` 默认就是这套行为，只是多了构建前端、查端口、记 pid 和日志。

### 如果 `npm install` 报 EPERM

这台机器上的 `~/.npm` 里有 root 属主的文件，npm 写缓存会被拒。项目已经带了 `.npmrc`
把缓存改到项目内的 `./.npm-cache`，正常情况下不用管。

想彻底修好全局缓存：

```bash
sudo chown -R $(id -u):$(id -g) ~/.npm
```

修好之后可以删掉 `.npmrc` 里那一行。

## 使用流程

1. **准备伴奏**：两条路都行 ——
   - **点歌台**：配好曲库源之后（见下文「曲库源」）搜索歌名/歌手 → 点「点歌」，
     服务端把伴奏下载入库（源站带了 LRC 的话歌词也一起进来），完成后点「去演唱」。
   - **伴奏库**：把伴奏文件拖进上传区，等状态从「转码中」变成可用。
2. **加歌词**（可选）：在伴奏库点「编辑」，粘贴 LRC 文本或选一个 `.lrc` 文件。
   每行都要有时间戳（`[00:12.00]`），纯文本歌词会被拒 —— 没有时间轴就没法跟唱。
3. **去演唱**：戴上耳机，选好麦克风（对着说话看音量条有没有反应）。
   设备下拉**只列外置输入**：MacBook 机身内置麦克风默认不出现（演唱要的是外置话筒，
   也不想把机身震动和风扇声收进去）。没插外置麦克风时下拉是空的、会提示插麦，
   「开始演唱」保持禁用 —— 不会偷偷回退到内置麦克风。
   下拉下面那行会写明**隐藏了哪些设备**，认错了（或者临时想用内置的）点「显示全部设备」即可。
   有歌词的话舞台区会显示逐行高亮的跟唱歌词，点某一行可以跳过去。
4. **开始演唱**：伴奏/画面开始播放，耳机里同时听到伴奏和自己的声音。
   两个滑块分别调伴奏音量和耳返音量；不想听自己的声音就把「人声耳返」关掉。
5. **结束演唱**：点按钮（或者伴奏放完自动结束）。干声上传后服务端立刻合成 MP3，几秒后跳转到作品编辑页。
6. **调混音 / 修音**（编辑页只有两块：实时试听 → 混音调整）：点「实时试听」播放，然后调
   人声音量/伴奏音量、混响档次、均衡、压缩、去齿音，
   以及「人声对齐微调」（滑块或直接输入毫秒数，范围 ±1000ms）—— 改动**立即**在试听里生效，不用等。
   满意后点「合成」：服务端用干声重新出一版 MP3，页面**直接返回作品库并定位到这首作品**，
   在列表里等「正在合成…」变成「已就绪」即可。
7. **播放 / 下载**：都在作品库列表页 —— ready 的作品直接内嵌播放，或点「下载 MP3」拿 192kbps 立体声文件。

> **实时试听里听不到的是降噪**：没有对应的 Web Audio 节点，只在「合成」后的成品里生效，
> 页面上有明确提示。

## 曲库源

「点歌台」的曲库不是内置的，而是读**你自己提供的清单**。原因很直白：网上没有免费公开的
「伴奏搜索」API，而商业在线曲库（如 ZEGO 在线 KTV）需要注册与付费。所以这里定义了一个
小而稳的协议，把源的差异挡在 provider 之外。

源站**只需要托管一份静态 JSON**，不需要实现任何服务端逻辑 —— NAS、对象存储、局域网 HTTP、
静态站点都能当源用，也不需要鉴权或反爬对抗：

```json
{
  "version": 1,
  "name": "我的伴奏库",
  "items": [
    {
      "id": "qingtian",
      "title": "晴天",
      "artist": "周杰伦",
      "durationSec": 269,
      "kind": "audio",
      "url": "qingtian.mp3",
      "lrc": "qingtian.lrc",
      "sizeBytes": 12345678
    }
  ]
}
```

- `id` 可省略，省略时用 `url` 兜底 —— 去重键必须在源内稳定唯一。
- `url` / `lrc` 相对或绝对都行（相对地址按清单地址解析）；只接受 `http(s)`。
- `lrc` 可选；有的话点歌时会把歌词一起入库，唱歌时直接能跟唱。
- 清单结果按 TTL 缓存在内存里，搜索是纯本地过滤，不会每敲一个字就打源站。
- 拉取失败时**回退到过期缓存**：源站抖一下不该让整个曲库变空；某个源挂了也只提示该源。

配置方式见下面「配置」里的 `LIBRARY_SOURCES`。**不配也能用**，点歌台会显示配置指引，
手动上传伴奏完全不受影响。

> 想要真正的商业曲库（千万级、带版权）需要接入厂商服务或为具体站点写适配器。
> 这两者都可以作为新的 `LibraryProvider` 插进来，不用改架构 ——
> 见 `server/src/library/types.ts` 的接口与 `providers/httpIndex.ts` 的参考实现。

## 工作原理

### 演唱页的音频图

```
<video>/<audio> ──MediaElementSource──┬──> accompGain ──────────────────────────────────────────────────────────────────────┐
                                      │                                                   │
                                      └──> AudioWorklet(accomp-onset) ──> captureSink(0)
                                                                                       │
MediaStreamSource ──> analyser ──> micMonitorGain ──────────────────────────────────────────────────────────────────────────────├──> destination
                  │                                                                       │
                  └──> AudioWorklet(pcm-capture) ──> captureSink(0) ──────────────────────────────────────────┘
```

三个关键点：

1. **录音只取麦克风干声**，耳返混音不写进录音文件 —— 这是后面能任意重新混音的前提。
2. `captureSink` 是个 0 增益节点，作用是让 Worklet 处在「被 destination 拉动」的路径上；
   没有它浏览器可能压根不调用 `process()`。
3. 全 App 共用一个 `AudioContext`，并且用 WeakMap 缓存 `MediaElementSource` ——
   `createMediaElementSource` 对同一个元素只能调一次。

### 对齐

干声 WAV 的 t=0 是**起录**时刻，而歌手是对着**起播后**的伴奏唱的 —— 干声第一拍
落在 WAV 时间 ≈ G（G = 起录到伴奏真正起播的间隔，含 150ms 预备静音和浏览器
seek/解码/调度延迟）。成品 MP3 里伴奏第一拍在 mix 时间 0，所以人声必须**提前 G**
才对得上，即最终偏移 `offset = userOffsetMs − autoOffsetMs`（可为负）。

1. 点「开始演唱」→ 立刻开始采集 PCM，记下渲染时钟 `captureStartCtxTime`
2. 等 150ms → `currentTime = 0; play()`，同时武装起播探测器
3. `accomp-onset` worklet 挂在 MediaElementSource 上（伴奏音量 gain 之前），
   用**渲染时钟**记下伴奏第一个非静音样本的时刻；`playing` 事件 / `currentTime`
   轮询作兜底（伴奏开头是长静音时 onset 偏大，取两者中更接近真实起播的那个）
4. `autoOffsetMs = G`（恒为正）；2.5s 内两个信号都没来回退到 150ms 常量并告警
5. 服务端按 `shared/mix.ts` 的 `mixTimeline(offset)` 决定延后哪一轨：
   offset ≥ 0 → 人声分支 `adelay`；offset < 0 → 伴奏分支 `adelay`（没有负 adelay，
   延后伴奏等价于把人声提前，干声开头那段静音正好被吃掉）

`adelay` 挂在 amix 之后就等于没对齐，所以它永远在 amix 之前的某一分支里
（有单元测试守着两个方向）。自动值之外还留了 ±1000ms 的人工微调
（正值 = 人声更晚 / 抢拍，负值 = 人声更早 / 拖拍），叠加在自动值之上。
老库作品会在启动时按 `align_ver` 一次性换算到新公式（`server/src/db.ts`）。

### 混音滤波器链

```
[0:a] aformat=48000/stereo, highpass=80, volume=<人声>, [aecho=混响], [adelay=<人声延迟>] [v];
[1:a] aformat=48000/stereo, volume=<伴奏>, [adelay=<伴奏延迟>] [a];
[v][a] amix=inputs=2:duration=first:normalize=0, alimiter=limit=0.95 [m]
```

- 两个 adelay 按 `mixTimeline(offset)` 二选一：offset ≥ 0 只延后人声，offset < 0 只延后伴奏。

- `duration=first` + 人声在第一位：成品长度跟着人声走，用户中途停不会拖出一长段纯伴奏尾巴。
- `normalize=0`：amix 默认会按输入数把音量除以 2，这里必须关掉。
- 响度归一化**没有**用 ffmpeg 的单遍 `loudnorm` 滤镜 —— 它的动态模式带内部前瞻缓冲，
  会引入不可控的时间偏移。改成「先跑一遍测量拿到输入响度，再乘一个静态增益」，零延迟且可预测。

### 跟唱歌词

LRC 文本存在 `tracks.lyrics`（**只存原始 LRC**，不存解析结果 —— 库里留一份会过期的解析结果是
自找麻烦），解析交给 `shared/lrc.ts` 在前后端各自执行，与服务端校验口径完全一致。
时间轴换算只有一条公式：

```
某行显示时刻 = 行时间 − [offset:] 标签 + 用户微调
```

`[offset:]` 正值 = 歌词更早显示（LRC 惯例），`userOffsetMs` 正值 = 歌词更晚显示（滑块语义），
两者方向相反是各自惯例决定的，`shared/lrc.ts` 里写死并有单测互相锁定（`lyricClockMs` 是它的逆运算）。

演唱页的当前行由 `requestAnimationFrame` 读 `mediaEl.currentTime` 自己算（**不用 `timeupdate`**，
它只有约 4Hz，歌词会一顿一顿地跳），只在「当前行变了」时才 `setState`，
再靠 `transform: translateY` + CSS transition 平滑滚动。

### 修音与音效链：为什么要有「人声预处理 pass」

均衡是双二阶（biquad）滤波，**没有内部延迟**，可以安全地留在混音图里。但修音用到的这些滤镜
都带内部延迟，而且延迟量随参数变、各滤镜还不一样：

| 滤镜 | 用途 | 延迟来源 |
|---|---|---|
| `acompressor` | 压缩 | 前瞻式动态处理 |
| `deesser` | 去齿音 | 检测 + 平滑窗 |
| `afftdn` | 降噪 | FFT 加窗 |

把它们挂进混音图，`adelay` 算出来的毫秒数就不再是真正的对齐量，而且**没法用一个常量补**。
所以这些处理统统放进**一次独立的人声预处理 ffmpeg 运行**（产出 48k 立体声 16bit 中间 WAV），
混音图拿到的是已经处理好的文件，`mixTimeline` 的语义一个字都不用改。

顺带两个好处：

- **原始 `vocals/*.wav` 永远不被改写** —— 参数随时可以重新调，这是「干声是任意重新混音的前提」。
- 参数全中性时**根本不跑**这次预处理，直接拿原始干声混音，与这个功能加入之前逐字节一致。

压缩的 makeup 补偿**故意不用** ffmpeg 的 `makeup` 选项，而是并进人声的线性增益
（`vocalChainLinearGain`）：Web Audio 的 `DynamicsCompressorNode` 没有 `makeupGain`，
预览得自己补一个增益节点，把补偿统一收进「人声线性增益」这一处，前后端就只剩一套公式。

音效预设**不是不透明滤镜串**，而是「一组具名默认值」（`VOCAL_PRESET_SPECS`）：点一下就把数值
写进 `eqLowDb` / `compression` / `reverb` 等字段，之后还能继续手调。这样预览与服务端天然同构，
也省掉「预设和滑块谁说了算」这类扯不清的推导。

### 实时试听（改参数不用等合成）

以前调任何参数都要点「重新生成」，等 ffmpeg 把整首 MP3 重编码一遍。现在作品编辑页的
「实时试听」在浏览器里用 Web Audio 复刻了同一条滤波器链，参数改动只操作本地音频图节点，
零网络请求、立即发声：

```
vocalBufferSource ──> vocalGain ──> highpass(80Hz) ──> eqLow ──> eqMid ──> eqHigh
                  ──> compressor ──> deEss ──┬── dryGain ──────────────┐
                                             └──> convolver ──> wetGain ─┤
accompBufferSource ──> accompGain ────────────────────────────────────────┼──> limiter ──> destination
```

- 音量滑块 / 毫秒输入 / 混响 / 均衡 / 压缩 / 去齿音的改动走 `onParamsChange` 直接进引擎；
  音量、混响、均衡、压缩都用 `setTargetAtTime` 平滑过渡，**不打断播放**。
- 均衡三段（低 200Hz / 中 1.2kHz / 高 4kHz）与服务端 `buildEqChain` 共用 `EQ_BANDS`，
  预览用 `BiquadFilterNode` 的 lowshelf / peaking / highshelf，**一一对应，不是近似**。
- 压缩的阈值与压缩比与服务端 `acompressor` 同源（`compressorParams`），makeup 已并进 `vocalGain`。
- 去齿音预览用**静态高架下压**近似服务端的动态 `deesser`；降噪（`afftdn`）预览里没有对应节点，
  直接跳过 —— 这两项属已知偏差，都在面板上标注了。
- 对齐偏移不用 `DelayNode`（改 delayTime 有爆音），靠「晚到的一轨晚起播」调度
  （offset ≥ 0 人声晚进、offset < 0 伴奏晚进，与服务端 mixTimeline 同一套规则）；
  偏移变化时防抖 120ms 后按当前位置重排两轨，无缝续播。
- 电平和成品 MP3 对齐：最近一次成功混音时实测的两轨增益（`works.levels` 列）
  随作品落库，预览按 `10^(dB/20) × 用户滑块 × 压缩补偿` 复算，和服务端 `computeLevels` 同一套公式。
- 混响是卷积混响对服务端 `aecho` 的**听感近似**（四档尾巴长度递进），最终音色以下载的 MP3 为准。
- 预览时长 = 干声时长 + max(0, 对齐偏移)，和服务端 `duration=first` 一致，播完自动停。
- 干声和伴奏在首次点「试听」时才解码（懒加载），避免只下载不试听的用户白占内存；
  接近 15 分钟的录音解码后约几百 MB Float32，是已知限制。
- 编辑页因此只剩「实时试听 + 混音调整」两块；成品 MP3 的播放/下载都在作品库列表页，
  点「合成」后带着 `focusWorkId` 跳回列表，滚动到位并高亮几秒。

多个源用逗号分隔；名字可以省略（省略时用清单里的 `name`，再不行用主机名）。
清单协议见上文「曲库源」。

## 日志

服务端所有输出走 `server/src/logger.ts`，单行格式（重定向到 `.run/openktv.log` 时自动去掉颜色）：

```
2026-09-20T16:21:21.166Z INFO  [track] 晴天（audio）→ 直接可用：mp3 可直接播放 id=54ed… artist=周杰伦
2026-09-20T16:21:21.166Z DEBUG [http] POST /api/tracks 201 48ms
2026-09-20T16:21:21.201Z DEBUG [ffmpeg] 启动 转码 video timeoutSec=1800
2026-09-20T16:21:35.268Z INFO  [job] 完成 mix:54ed… costSec=3.2
2026-09-20T16:21:40.001Z ERROR [job] 失败 mix:54ed… error=Error: 混音超时（300s）已中止
```

- **级别**：`LOG_LEVEL` 控制，低于阈值的完全不输出；`warn`/`error` 走 stderr，其余走 stdout。
- **作用域**：`http`（请求方法/路径/状态码/耗时）、`job`（入队/开始/完成/失败）、`track`、`work`、`mix`、`ffmpeg`、`probe`、`db` 等。
- **降噪**：`/api/health`、`/api/media/*` 这类轮询/流式请求只记 `debug`，正常刷页不淹没问题行。
- 想看某个任务的 ffmpeg 参数、响度测量值这类细节就 `LOG_LEVEL=debug`。

## 常见问题

**录出来的人声断断续续 / 发闷 / 声音特别小**

浏览器自带的「降噪（noiseSuppression）」和「回声消除（echoCancellation）」是给语音通话做的：
降噪用谱减法把持续成分当噪声削掉，唱歌的长音正好符合“持续噪声”的特征；
回声消除又会把耳返里放出的自己的声音当成回声去自适应抵消。
两个叠在一起，听感就是一段一段还发闷。

本项目**已经默认关掉了它们**（`getUserMedia` 里显式传 `false`），因为那是给通话用的，不是给唱歌用的。
系统自带录音机不走这套处理，所以它录出来是正常的 —— 这也是判断依据。

如果还是断断续续，按顺序排查：

1. **设备/驱动强制开着处理**。演唱页录完会检查实际生效的设置，如果驱动硬要开，页面会明确告诉你，
   并让你去系统声音设置里关掉「环境降噪 / 语音隔离」之类的选项。
2. **采集真的在丢片**。工作线程每拍拿不到输入时会补静音并计数，丢片超过 0.5% 页面会提示。
   这种情况关掉别的吃资源的程序（视频通话、大型软件）、或换个麦克风接口再试。
3. **采样率不匹配**。麦克风常见是 44.1kHz，本项目不再强制 AudioContext 用 48kHz，
   避免在设备时钟有偏差时多插一级重采样导致周期性丢样本。录进来是 44.1k 也没关系，
   服务端混音时会统一重采样到 48k。

**啸叫 / 听到回声**
麦克风通过外放把伴奏收回去了。戴耳机 —— 关掉回声消除之后，这一点比之前更需要注意。

**耳返拖拍**
蓝牙耳机延迟普遍 150ms+，Web Audio 直连监听救不了。换有线耳机。

**音量条不动**
麦克风选错了，或者系统层面被静音了。换个设备再对着说话试试。

**下拉里没有我的麦克风**
下拉只列外置输入，内置麦克风（`MacBook Pro麦克风 (Built-in)` 这类）默认隐藏，
Chrome 的「系统默认设备」别名也一并藏了。插上 USB / 3.5mm 麦克风后会自动出现；
没插麦又非要用内置的，点下拉下面那行提示里的「显示全部设备」。
那行提示会把**被隐藏的设备名**也写出来，一眼就能看出是不是认错了。

**「开始演唱」是灰的**
说明麦克风还没接进音频图。看按钮旁边的提示文字：可能是权限被拒（点「重试授权」）、
没有可用的外置麦克风（插上麦克风就行，内置的没算数），或者还在初始化。

**转码失败 / 服务重启把转码打断了**
失败的伴奏卡片上会有「重试处理」按钮。原文件还在，点一下重排转码，不用重新上传。

**伴奏删不掉**
被作品引用了。服务端会拒绝（409）并告诉你有几个作品，先去作品库删掉那些作品。

**成品里人声和伴奏错位**
去作品库点「调混音」进编辑页，开「实时试听」边播边调「人声对齐微调」（拖滑块或直接输入毫秒数，
范围 ±1000ms）—— 改动立即生效，对到位后点「合成」，返回作品库等「已就绪」再下载。

**伴奏的调太高/太低，唱不上去**
这个项目**不做升降调**（曾经的「音调」面板已经去掉）。想换调就先用别的工具
（Audacity、ffmpeg 的 `rubberband` 滤镜等）把伴奏移调，再把移调后的文件传进伴奏库唱。

**歌词对不上 / 整体快半拍**
先在伴奏库「编辑」里确认 LRC 的时间戳本身没错；再到演唱页用「歌词对轴微调」整体挪
（正值 = 歌词更晚出现，范围 ±30s），改完自动保存。
如果 LRC 里有 `[offset:]` 标签，它会和这个滑块叠加 —— 两者方向相反，见上文「跟唱歌词」。

**歌词贴进去报「至少要有一行 [mm:ss] 时间戳」**
这个项目只支持带时间轴的 LRC：没有时间戳就没法滚动跟唱，所以宁可报错也不静默降级。
给每行加上 `[00:12.00]` 这样的前缀即可。另外只认 UTF-8 编码，GBK 的 LRC 会解析不出内容。

**点歌台说「还没有配置任何曲库源」**
这是预期行为：本项目不自带曲库。用 `LIBRARY_SOURCES` 指向你自己的清单地址即可
（协议见上文「曲库源」）。不配也不影响手动上传伴奏。

**点歌一直停在「下载中…」或者报源不可用**
源站拉清单失败会回退到过期缓存，但真正下载失败就没有退路。看看服务端日志里
`[library]` 那几行；服务重启会让进行中的任务状态丢失（轮询会拿到 404），重新点一次即可。

## 已知限制

- 只保证桌面 Chrome / Edge；Safari 和手机浏览器没做兼容。
- **不做音准 / 节奏打分**（这是相对全民K歌最大的空缺），不做原唱伴唱切换（需要人声分离）。
- **曲库靠你自己提供清单**：没有内置授权曲库。在线搜索到的内容取决于你配的源，
  服务端会真的去下载它 —— 请自行确认来源的合法性与可用性。
- **实时试听里听不到降噪**：没有对应的 Web Audio 节点，只在「合成」后的成品里生效，面板上有提示。
- 去齿音的实时试听是**静态高架下压近似**，成品用的是动态 deesser；绝对音色以成品 MP3 为准。
- **不做升降调**：伴奏调不合适请用外部工具移调后再上传（见「常见问题」）。
- **演唱只列外置输入**：Web 平台没给设备类型字段，只能按 label 认内置麦克风
  （`web/src/utils.ts` 的 `isBuiltinMic`：机型名 / 「内置」/ `Built-in` / `Internal`，
  外加 Chrome 的「系统默认设备」别名；名字里带「外置 / 外接 / USB / 蓝牙」的一律算外置，
  因为 3.5mm 耳机口那个外接麦的传输类型 macOS 也报成 `Built-in`）。
  名字起得古怪的设备仍有可能判错，下拉下面那行会列出被隐藏的设备名，
  点「显示全部设备」就能把它们放回来。
- 歌词只认 **UTF-8** 的 LRC（BOM 容忍）；GBK 编码会解析出 0 行并明确报错。
  纯文本歌词（没有时间戳）会被拒，不做在线歌词抓取，也不做自动转写。
- 作品/伴奏编辑与点歌都要求同一首伴奏只关联一份歌词，不支持多语言歌词或双语对照。
- 一次只跑一个 ffmpeg 任务（单机自用，避免抢 CPU 影响耳返）。
  开了修音的人声预处理 pass 要多跑一次 ffmpeg，合成会比之前慢一些。
- 无登录、无多用户、无公网部署加固；默认只监听 127.0.0.1。
- 点歌台会向**你配置的**源站发出站请求；源站不可用时会提示该源失效（其他源不受影响）。
- 磁盘不做自动清理，作品和伴奏都要手动删。
